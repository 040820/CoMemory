# LiCoMemory 事件与状态演化层设计（第一版）

## 目标与范围

在现有 Chunk 原文和 Triple 事实索引之上，增加独立的状态索引，记录单值状态的当前值和真实变化。每个状态与变化均可追溯到已有实体、Triple、Chunk。第一版保留原始 LiCoMemory 写入、检索及已生成图作为对照，不覆盖历史对话或实验结果。

第一版只处理可比较的单值属性。初始受控属性为 `employer`（当前雇主）、`job_title`（当前职位）、`residence`（当前常住地）；属性表可扩展，但新名称必须显式加入配置和同义词映射。普通活动、可并存的兴趣和没有持续状态含义的事件仅保留在原有 Chunk 与 Triple 中。

## 已选择的方案

- **独立状态索引（采用）**：新增写入模块和独立数据库，不修改原有图结构；新检索器可选择读取状态索引。便于保持 Baseline 和比较实验。
- 直接修改 CogniGraph：结构统一，但现有 `DiGraph` 对相同实体对的关系会合并，Triple 也没有稳定 ID；要保留历史需重写存储与迁移旧图。
- 查询时临时推断变化：写入简单，但每次重复判断，纠正和跨会话时间线难以保持一致。

独立索引建议使用 Python 标准库 SQLite，放在新实验工作目录。写入一批状态、变化和证据链接时使用同一事务，失败则整体回滚。数据文件不提交 Git；模块代码、配置、实验说明提交 Git。

## 数据模型

| 记录 | 关键字段 | 用途 |
| --- | --- | --- |
| 实体映射 | `entity_id`, `graph_entity_name`, `aliases` | 将稳定 ID 对应到现有图节点；名称不明确时不自动合并不同人。 |
| 事实引用 | `fact_id`, `entity_id`, `attribute`, `value`, `triple_subject`, `triple_predicate`, `triple_object`, `triple_ref`, `chunk_id`, `session_id`, `status` | 给状态事实一个稳定 ID；保存对应的中层三元组语义，`triple_ref` 是可选的已有边定位信息，`chunk_id` 是必需的原文证据。 |
| 当前状态 | `(entity_id, attribute)`, `value`, `fact_id`, `observed_at`, `status` | 按实体和属性快速得到当前有效值。 |
| 变化记录 | `change_id`, `event_group_id`, `entity_id`, `attribute`, `old_value`, `new_value`, `event_time`, `observed_at`, `detection`, `status` | 只记录真实状态变化；`detection` 区分原文明确表述与前后状态推断。 |
| 证据链接 | `owner_type`, `owner_id`, `fact_id`, `chunk_id`, `triple_ref` | 由当前状态或变化回到具体事实和原文，也支持从事实反查变化。 |

中层现有 Triple 没有稳定的独立 ID，且 `DiGraph` 合并边可能丢失关系版本。因此新索引分配自己的 `fact_id`，不能把可变图边的位置当作长期 ID。每条入库的状态事实都必须对应一个中层三元组和一个原文 Chunk：在旁路索引中固化三元组的主语、关系、宾语，并映射到已有实体索引；`triple_ref` 额外定位仍可找到的现有图边。若无法确认三元组与 Chunk 属于同一事实，进入待核查队列，不创建状态或变化。写入时还记录原文片段，供核对关系和说话者。

`event_time` 表示事件实际发生时间，可为空并保留日期精度；`observed_at` 表示本系统从会话得知它的时间。未明确提及发生日期时，不能用会话日期冒充 `event_time`。`status` 表示当前有效、已纠正、已取代或待核查，不用相似度或使用次数代替事实有效性。

## 写入流程

1. 沿用已有对话分块与 Triple 提取，保存 Chunk 原文；新模块在此之后读取新增 Chunk、相关 Triple 和会话时间。原始写入算法保持可单独运行。
2. 从新增证据识别受控属性的候选状态，解析主体和规范化值。LLM 只对“候选证据、同一实体同一属性的当前状态及其证据”作结构化判断，不让模型凭世界知识补充旧状态或事件时间。
3. 首次得知属性值：创建当前状态基线及证据链接，不生成变化记录，也不虚构 `old_value`。
4. 新值与当前值不同，且原文明确表达变化或新旧会话分别支持不同的当前值：更新当前状态，追加变化记录。即使新会话只说“我现在在 C 公司”，旧状态为 B，也记录 B → C；将 `detection` 标为推断。新旧证据均挂在该变化记录上。
5. 原文明示此前说错、抽取错或“从来不是 B”：视为纠正。先定位被纠正的具体事实，将其标记为已纠正；它参与的推断变化标记为已撤销，并根据剩余有效证据重算该实体、该属性受影响的后续时间线。若被纠正的正是当前事实，覆盖当前有效状态的指针；若被纠正的是历史事实，后来独立证据支持的当前值继续有效。例如一月的 B 被纠正为 A，而二月、三月的 C、D 仍有证据时，当前值仍是 D。不把错误的 B → C 写成真实事件，重算后的 A → C 若有足够证据则标为推断。旧事实记录留在索引中供审计，Chunk 原文不删除。
6. 新信息与当前状态一致：可增加支持证据，不重复创建变化。主体、属性或证据无法确认时进入待核查队列，不覆盖当前有效状态。

第一版按已有会话的时间顺序增量处理；不支持把更早会话乱序补录后自动重排全局时间线。若将来需要补录旧会话，应单独执行该实体、该属性的重建流程。当前会话中的“过去曾在 B 公司”这类回顾性陈述只补充历史证据，不直接取代当前状态；不能仅凭较晚被系统看到，就断定事实较晚发生。重复处理同一来源 Chunk 时按稳定来源键去重，避免重复生成基线或变化。

每个变化记录只对应一个实体和一个属性。同一次真实事件若改变多个属性，分别生成变化记录并共用 `event_group_id`；不能仅因它们出现在同一会话或同一天就合并。组内变化必须有共同的事件依据。

## 索引与查询

- 正向索引：`entity_id → attribute → current_state / ordered changes → fact_id → Chunk`。查询当前值和历史变化分别走当前状态与变化记录。
- 反向索引：`fact_id / chunk_id → change_id`，从已有中层事实快速找到相关变化。
- 当前状态问题使用有效状态及其原文证据；历史问题按时间线返回相应版本。若事件时间缺失，只能表述记录先后，不能断言真实发生日期。
- 新检索器增加可关闭的状态索引入口。对当前状态问题，已纠正或已取代的事实不能作为当前答案依据；历史问题仍可读取旧 Chunk。原始 LiCoMemory 检索路径不修改。

## 验证与边界

验证重点包括：首次事实不产生虚假变化、隐含的新旧值冲突产生可追溯变化、明确纠正撤销错误变化、同一事件的多属性分组、不同人同名或同一人的别称、时间未知时不伪造日期，以及从实体和证据两端都能找到变化。回答实验应固定同一回答模型与提示词，比较有无状态索引时的当前状态、历史状态和纠错问题，并保存逐题证据与误判记录。

第一版不追踪多值属性、普通事件、无明确主体的状态，也不自动回填现有图中已丢失的关系。若未来需要从旧 `.pkl` 构建索引，应作为单独的只读迁移流程，并记录无法唯一映射的事实。
