# 面向 QA 的事实关联与记忆演化设计

日期：2026-10-30。适用工作区：`D:/Code/LiCoMemory`。本文为设计，不代表新能力已经实现或验证。

## 1. 目标与边界

针对 LoCoMo 和 LongMemEval，在已有 Fact 构建中产生可追溯的事实关联，并为证据充分的状态变化和纠正提供独立决策与状态版本；查询时按需使用关联、状态和原文。最终以 QA 准确率为主要效果指标，分类报告更新、时间、多会话和其他问题；同时检查错误更新、证据支持与成本。

必须保留当前原文、完整 Triple 出现记录及来源校验。不能为了提高召回而将无依据的断言放入记忆：失败候选仍进 `review_queue`/`skipped_candidates`。事实关系是检索线索，更新决策是另一个有证据的结果；二者均不等于客观真值。模型置信度与检索分数不得独自触发更新。

LoCoMo sample0 曾用于开发；此前 pilot 17 题只用于诊断，不能作为独立留出结果。LongMemEval 每题保留完整 haystack；gold 答案、来源和人工标签只用于评价，不进入构图、检索、审查或 Reader。

## 2. 当前基线与方案选择

当前代码和配置：

- `config/Memory_EventState_sample0_rebuild.yaml` 选择 `entity_fact_index + event_index + append_only`。`GraphBuilder` 的 NetworkX 无向实体关联边索引 fact ID，`TripleFactStore` 保存完整 Triple；Chunk 原文在 `chunk_storage`。
- `EventStateWriter` 校验原文和 Triple 后追加 Observation，通过同槽/语义等路径召回历史并记录候选 `fact_relations`。活动也有候选关系；当前不提交替换或纠正。
- `lean_event_index.pack_event_index` 只接受未裁决的 append-only 图，持久化事件组及候选 links；模型轨迹等另存内容寻址审计。不能原样把有 current/events 的旧 gated 层塞进现有格式。
- `EvidenceSupport.review_pair` 对已保存的新旧端点检索并审查，返回提议且 `update_applied=false`。问答沿 Chunk Top-5 → 选择 Observation 锚点 → 多路取证/Judge/Reader；其实际展示窗口与候选池不同。
- 既有 `confidence_shadow` 未校准、独立性未验证，且不参与决策。已有 30 对关系标注模板没有人工金标，不能报告关系正确率或校准效果。

比较方案：

1. **只做问答期原文补查**：不改构建，开发和额外写入成本低；但难以稳定复用新旧事实关系，也无法解释已提交状态。适合作为补充对照，不满足已选目标。
2. **Fact 构建时登记关系，更新按证据门控，问答按需补查（选用）**：复用现有 Fact 和候选关系，普通 QA 可用关联补查，更新题可用状态版本；需要明确额外构建成本、存储版本和证据边界。
3. **另建完整图数据库并改写全链路**：表达灵活，但迁移、运维和变量较多，不能证明新增数据库本身改善 QA；本阶段不采用。

默认先运行 `shadow` 研究模式，再在隔离环境验证 `review` / `gated`。默认线上行为和已有实验不改变。用户已明确选择第 2 种总体方向；分项工程选择和预算是本设计建议。

## 3. 对象与不变量

复用现有 `Chunk`、原始 `Triple`、`Observation`、事件组；它们不要求都变成 NetworkX 节点。新增加版本化 `Decision` 和 `StateVersion`，并提供可重建索引。约定：

1. **Observation 是用户或对话来源的说法**，不是已独立证实的现实真值。Fact 原文、原始属性/值、模态和来源不被派生规范化值覆盖。
2. `related`/`complement`/`coexists` 等允许作为带来源的候选检索边；`replacement`/`correction` 必须经过额外审查，不直接改变状态。`unrelated` 和失败记录保存在审计，不加入检索关联图。
3. 原始 Chunk、Triple 和通过校验的 Observation 保留；旧状态版本与决策可回溯。单值状态存在未决冲突时，不能只因旧状态曾有效就输出确定的当前值。
4. 状态变化与事实纠正分开：变化保留历史有效性；纠正标记旧结论被纠正及其原因。跨主体纠正可指向旧主体断言并新增新主体断言，不能由同槽约束静默丢掉。
5. 实体名并非可靠全局身份。实体不确定时不自动合并或提交跨主体更新；用已有实体 ID 加上下文、来源、审查结果记录歧义，不凭同名断定同一人。
6. 区分事实极性（肯定/否定）与模态（现实/计划/假设）。当前 `slot_key` 把 `negated` 放入模态，正反断言可能落在不同槽；候选比较需要显式跨极性检查，但不自动判冲突或替换。迁移保留原始模态、引文及来源，不能把派生归一化结果当作真值。

### 3.1 证据与决策建议结构

`EvidenceRef`：`chunk_id`、`fact_id`（可空仅用于非结构化原文）、`start/end`、`quote`、`role`（`old`/`new`/`transition`/`support`/`refute`/`context`）、来源时间、引文校验结果。位置使用 Chunk 文本的 Python 字符索引、左闭右开；持久化时保存原文 SHA256 和索引规范版本，重新加载时验证 span 与 quote。多个证据可指向同一个 Chunk，不默认为独立来源。

`Decision`：稳定 `decision_id`、`old_fact_ids`、`new_fact_ids`、`candidate_relation`、`action`、`decision_status`、`evidence_refs`、结构化检查、自然语言理由、`model/prompt/policy` 版本、`knowledge_cutoff`、完整输入依赖、`decided_at`、`input_revision`、`applied`、错误类型。状态包含 `proposed`、`pending`、`approved`、`committed`、`rejected`；技术失败和语义不确定记录不同原因。模型提议、程序策略结论与提交结果独立字段，不覆盖彼此。状态转换追加带顺序号的 Decision 事件，以便重建任一知识时点；先前 proposal 不能被覆盖成后来的 commit。

`StateVersion`：`state_version_id`、`slot`（实体、规范属性、作用域、模态）、`value`、`source_fact_ids`、`decision_id`、`valid_from/valid_to`、时间范围/精度/依据、`known_at`、`status`、前一版本 ID。`known_at` 指数据源提供的说法观察时间；另存系统实际处理/决策时间。未知时间保持 null，不因“今天说”自动填充有效起始或结束时间。事实时间不精确时保存范围，而非伪造精确日。

对于单值状态，有效期未知时不得简单以 null 视作无限有效；读取返回 `known / unknown / conflicted` 及证据，按已有事实与决策生成视图。集合属性允许多值；无充分基数依据默认保守，不能用同一开放谓词的不同值推断替换。

## 4. 构建与更新链路

```text
Chunk → LLM 提取 → 原文/主体/Triple/模态校验 → Observation 保存
                                      ↓
                         历史候选召回及路径记录
                                      ↓
           普通关联候选                         涉及变化/纠正的候选
      可用于检索定位，不等于真值           → 读取双方及相关反证 → EvidenceSupport
                                                   ↓
                                       UpdatePolicy → Decision
                                                   ↓
                                     仅受控模式提交 StateVersion
```

同会话内已有 Writer 顺序和双路召回按实际实现运行；不以注释声称的顺序替代轨迹。先完整保存合格的新 Observation，再生成关联/决策；关系判断失败不能丢弃已有原文支持的独立新事实，抽取本身失败不得放宽校验。

当前 `review_pair` 只接受已存在的 Observation，`add_single_session()` 本身也不落盘；新实现须先在单会话独立临时图上暂存并验证该 Observation，再构造只读 staged graph 供审查，不把未经校验的对象伪装成已提交事实。审查结束后由调用方以原子快照提交 Observation、决策事件与允许的状态版本；若关系审查失败，仍可只提交通过来源校验的 Observation 和失败/待审记录。跨主体纠正通过明确纠正引文触发专门的旧主体/目标定位路径；不能放宽现有普通同主体召回来猜测关联。每条审查的输入集合、结果和失败均纳入同一审计版本。

动作定义：`ADD` 建立有充分来源的独立状态/事件；`SUPPORT` 关联新证据和已有断言；`KEEP_BOTH` 证据支持互不排斥；`UPDATE` 明确状态发生变化；`CORRECT` 明确旧说法/归属错误；`PENDING` 关系、目标、证据或时间不足。`ADD` 不意味着历史搜索已穷尽，也不能借召回失败证明没有旧状态。

状态变化门控必须满足：来源和引用有效、主体/属性/作用域/模态可比较、明确的变化依据可定位、时间不矛盾且目标明确、关键反证已考虑。纠正需要有明确纠正依据；涉及主体变化时验证旧指向和新主体。仅新值不同、时间更新、同槽或模型 `same_slot=true` 均不足以通过。缺失、截断、网络失败、语义不足、多目标歧义均转 `PENDING` 并保留原因，不能把技术失败算正确拒绝。

`shadow` 只写可独立评估的决策建议，`applied=false`；`review` 保存待审并在明确审查结果后提交；`gated` 满足政策才提交。初版默认 `shadow`，测试/评估配置显式切换，禁止使用当前未校准置信度作为自动提交条件。语义支持仍需人工金标和独立评测，程序门控通过不等于证明真实。

成本控制：仅对来源合格、可能存在历史关联或明确纠正线索的候选触发有限审查；候选数、补查轮数、来源和 token 预算可配置并记录实际调用。普通 Fact 不强制走全量模型审查。每条新 Fact 没有找到历史候选时记录召回范围及降级状态，不声称无历史事实。

## 5. 持久化、并发与迁移

新 schema 示例为 `event_index_v2`，保留 `fact_storage`、`event_state_layer.groups/links`，增加 `decision_store`、`state_version_store` 和 `schema_version`；语义以最终实现的 schema 为准。索引是可重建派生结构，不是唯一事实来源。现有 v1 严格按旧语义只读加载，历史候选 links 不自动转换为已确认关系或状态；需要状态历史时在独立新目录重放原文与候选，并记录原图、配置、源码及输入哈希。

首版采用现有 pickle 与内容寻址审计方案：先准备不可变审计/证据内容，构造包含决策、状态版本及索引的新快照并校验所有引用，再用同目录临时文件 + fsync + 原子替换提交主快照。快照只指向已写入的审计内容；失败时旧图、旧状态和旧审计仍一致。跨进程单写入者锁覆盖 revision 检查直至替换：模型调用放在锁外，提交时重验输入 revision；发生冲突须重新审查或暂缓，不能用一次非原子检查伪装 CAS。逻辑幂等键由新旧来源、目标、动作、政策和证据版本构成，独立于存储 revision，重试或恢复不重复生成同一生效版本。测试覆盖写审计后、主快照替换前/后中断，验证不能出现悬空引用或半次提交。不得修改旧图、实验结果或人工标注。

## 6. 查询与时间可见性

保留 `EvidenceSupport` 的当前原始 Chunk/Triple 候选与 Judge/Reader 路径。扩展发生在初始候选后：

1. 基于实际召回的 Fact，按问题与路径类型补充相邻 Fact 的来源、事件组或已确认决策；候选链接只作搜索入口，未知关联不当已证实内容。
2. 普通问题使用原文、事实与可用补充证据；当前状态题查可见状态及 pending 冲突；历史题查历史版本；原因题必须展示决策所需的旧、新和变化依据。缺失时明确不确定。
3. 分开 `valid_time`（问哪个事实时刻）与 `knowledge_cutoff`（当时可知内容）。当前 `as_of` 主要按来源观察时间过滤，不能当成已实现的有效期查询。重放时以数据源观察时间构造知识可见性；系统真实执行时间另存，不能因为实验实际运行于数据集日期之后而屏蔽全部历史。
4. 所有候选、锚点、归一化结果、图扩展、状态版本、Decision、关联端点、Judge 窗口和 Reader 实际原始 Chunk 都必须通过同一可见性限制；一次决策依赖未来证据时不能用于过去视图。派生关联/归一化/决策的逻辑可见时间至少是其全部输入来源的最晚可见时间；无法核定完整输入时在该时间点重新计算或标为不可用。未知时间的内容按协议显式处理，不填入虚构时间。
5. 有效期未知不是精确历史：对不能判断某时是否成立的状态标记 unknown，并保留能在截止时间看到的原文，不把旧说法当作确定当前状态。

对照实验沿用各数据集既定时间协议：LoCoMo pilot 为 `as_of=None`，不能在改造组自行添加仅其拥有的截止时间；LongMemEval 使用原生 question_date（保留分钟）。如另做严格历史截止实验，必须单独定义并对所有对照组一致实施，不与原口径混报。

控制上下文预算：每个对照组固定最终展示预算；关联路线可保留少量名额，但必须记录其挤掉的原候选。要记录初始候选、扩展新增、去重、排序、被截断项、最终展示窗口和答案引用，防止图扩展只在已满的候选池上做无效工作。

## 8. 评估与验收

### 8.1 QA 主实验

预先冻结同一数据集切分、问题、原始语料、base graph、模型、参数和答案评分协议，随机种子和代码/模型/图指纹。每个 LongMemEval 问题保留完整 haystack；原生 gold 仅在独立评分阶段使用。

| 组别 | 控制 |
| --- | --- |
| A 当前基线 | 既有 graph/查询/Reader，关闭新增扩展；确保基线行为与原结果一致。 |
| B Fact 关联 | 同一 base graph 加独立可见关系 overlay；只用于按需补查，不提交状态版本。 |
| C 关联＋更新决策 | 与 B 使用同一 base graph/overlay，增加独立生成的可追溯状态/决策视图；实验性受控提交只在新输出目录。 |

不得把新 overlay 混进 A 的基础图；所有组相同最终证据/上下文预算、LLM、评分和失败计入分母方式。A 使用新版本的 off 模式，并先用固定输入验证其与指定旧版本行为等价；上一轮 pilot 使用冻结源码，不能把新运行直接宣称为原结果。另报额外构建、审查、推理调用和时间；冷/热缓存分别记录。A/B/C 按相同题目配对，报告总体及各类 QA 结果、每题 A→B→C 变化和置信区间/样本量；区间按独立会话/样本聚类，不能将同一 LoCoMo 对话中的问题视为独立会话。小样本只称诊断。不可回答单列拒答和错误前提识别；技术失败、无答案、评分未知必须单列并保留总分母。相同模型自评只作代理，人工复核评分边界和分歧；逐题保存 gold、候选、展示、推理及评分轨迹，但 gold 禁止进入输入。

特别审查 LoCoMo q71 的正确轮次遗漏、q75 评分误判、q115 引文不足和 q194 主体混淆；它们用于开发回归，不作为独立泛化证明。LongMemEval 单题直接读到最新值不能单独证明系统执行了安全更新。

### 8.2 决策、置信度与解释

建立独立标注集合：从完整原文先标注新事实应关联的旧事实、证据角色、关系和期望操作，再与模型输出比对；既包含已召回，也包含漏召回对象。标注人不能看到待评模型输出；有歧义标为 unknown，分歧记录并仲裁。样本覆盖明确状态变化、事实纠正（含跨主体）、多值并存、重复、补充、不同事件、时间未知/乱序、无证据和干扰上下文。

报告受影响事实召回（含无候选）、关系混淆矩阵、更新精确率/召回率、错误覆盖率、应暂缓样本的错误提交率、正确可执行样本的漏更新率；逐项列分母和失败。`shadow` 是模拟决策，不能冒充真实持久化结果；`gated` 另测提交前后历史与当前读取、恢复和并发。

置信度先作为未经校准的等级：报告各等级的人工正确率、样本数、覆盖率及暂缓风险；不能把检索分数、引文存在、模型支持和更新充分性混成一个可靠概率。足够独立样本且确实输出概率后才考虑 ECE/Brier；训练/校准/测试分离。解释分别报告引用定位通过率和人工证据语义支持率；可逐字匹配不等于支持动作。

### 8.3 分阶段验收

1. **存储与影子决策**：旧图完全可读、新图独立写入；严格证据校验、候选/决策/状态分离；失败与中断可恢复；可生成完整逐条审计。
2. **关联检索**：记录路径、候选增量、预算淘汰和最终窗口；无未来来源泄漏，普通 QA 的基线组与既有行为一致。
3. **受控提交**：合成边界和人工审核样本中，该更新、不得更新及不确定三类均可判断和追溯；出现错误可用决策和状态版本定位，不覆盖原文。
4. **QA 对照**：A/B/C 固定数据和预算完成配对评估，报告总分、分类型、损益题、证据轨迹和代价；没有独立评估或样本量不足时不宣称提升。

本设计不承诺预设提升幅度。只有对照完成并结合人工核查后，才能总结实际效果；设计预期是改善证据覆盖、更新题正确性与可解释性，同时避免普通问答退化。
